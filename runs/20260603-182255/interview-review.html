同一份 trace，谁更值得把生产力任务托付出去？

这份作品把 Opus 和 DeepSeek 跑同一个视频 workflow（工作流）的 trace（执行轨迹）翻译成产品判断：质量是否同档、性价比差多少、过程能不能托付、出错能不能自救。一轮干净对比的诚实结论是——没有单轮赢家，是一组取舍。

工具抽取 = 纯规则 grader 从 metrics.json 自动抽取，可反查源文件 产品判断 = 我基于数据撰写的产品结论，模板生成不了

质量基本同档，性价比小幅有别，方向取舍清晰。 产品判断

两个模型都把视频交付了：3 张真实图片 + 3 段真实 TTS（文字转语音）拼成片、硬字幕烧录、55/55 质量检查全过、4/4 门禁一次通过、0 安全泄露，而且都从一个注入的失败里自己恢复了。门槛层面两边都过关。

差异在过程画像：Opus 研究更可审计（7 vs 5 个来源域名）、执行更干净（0 vs 4 个工具错误）；DeepSeek 更快（约 16%）、略便宜（约 10%），并把时长精确卡在 30 秒。

决策建议：关键 / 研究严谨 / 低容错任务用 Opus；规模化 / 成本速度敏感 / 流程清晰任务用 DeepSeek。

置信度
单轮观察（n=1），只能作为信号，不能写成稳定结论。差距温和（成本约 10%、速度约 16%），需第二轮确认是否复现。

②

为什么这么评

产品判断 把生产力任务托付给 Agent（智能体），风险从来不在"它能不能做出一个视频"，而在过程：它有没有读懂项目规则、会不会复用现成 workflow、失败后能不能自己爬起来、安全边界守不守得住、人工要盯多紧。所以我们不评最终视频好不好看，评 trace（执行轨迹）暴露出的过程差异——这才是决定"能不能规模化托付"的东西。

视频只是统一任务载体（统一考场）。真正评的是：Agent 能否把一句模糊目标稳定推进成可验收结果，并把过程沉淀成可复查证据。

③

怎么评（受控方法）

产品判断 拿同一个视频 workflow 当统一考场，锁住四件事：同一精简 prompt（只给目标和边界、不喂步骤）、同一 sandbox baseline、同一工具边界和检查命令、隔离 worktree（后跑的看不到先跑的）。所有判断只来自 trace 和 manifest（产物清单）。

1. 锁变量

同任务、同 baseline、同检查命令；两个模型互相看不到对方产物。跑前用脚本校验 sandbox 不含评测文件（防泄题）。

2. 留轨迹

保留 stream-json、stderr、diff、manifest、报告和检查结果，作为本地证据层。

3. 抽指标

纯规则工具抽成本、耗时、来源域名、错误、安全、一次通过率、失败恢复。

4. 做决策

门槛指标证明都能干活，区分指标支撑"什么场景用谁"。

④

我做的评测工具（作业核心）

产品判断 raw trace 又长又技术，产品面试官没法直接读。我的工具把它压成"产品能看懂的证据、档位和结论"。三个工具全是纯规则代码，零 LLM 调用——这是"客观"的根。

工具角色怎么工作（原理）用 LLM 吗
compare-traces.mjsgrader（评测器）读 trace.stream.jsonl + 各 manifest → 用计数和正则抽信号（读了哪些文件、跑了哪些命令、几个错误、成本/耗时、来源域名数、canary 是否泄露、MEDIA_005 是否恢复）→ 用写死规则打档 → 输出 metrics.json + report.md❌ 纯规则
render-interview-html.mjs展示器（数据版备用）读 metrics.json 套模板渲染；无判断、纯渲染。本页的软叙事由人撰写，工具版仅作数据对照备用❌ 纯规则
check-sandbox-baseline.mjs公平性校验跑前扫描 sandbox baseline，确认不含评测仓文件 / prompt / 计划，避免被测模型偷看评分标准（防泄题）❌ 纯规则
为什么坚持纯规则、不用 LLM 当裁判：同一份 trace 跑十遍结果完全一样，每个档位都能反查到是哪条规则、哪个字段算出来的。这避免了"用一个 AI 主观评判另一个 AI"的不可复现问题。客观 = 标准人定、数据机器从轨迹自动抽，不是我拍脑袋打分。软质量（研究深不深、报告好不好）目前用可量化代理信号近似；要评更深，下一步可加 LLM 辅助评分层，但会和确定性指标分开标注。

⑤·补 · 一套引擎 + 一个任务适配器（可复用性）

产品判断 我交付的不是"Opus vs DeepSeek 谁赢"的一次性答案，而是一套能持续评 Agent 的方法。工具天然分两层——换任务时，引擎不动，只换适配器。

⑦

失败恢复故事

产品判断（取材自 trace） sandbox 注入了一个 MEDIA_005 媒体失败：不自动兜底、不提示存在与修法，模型必须自己发现并恢复。两个模型都恢复成功了，但路径很不一样——这比一个错误数字更能说明"要不要人盯着"。

Opus：深度根因，零返工

  1. video:compose 拼接失败，主动去看完整 ffmpeg 报错，没有瞎试。
  2. 挖出根因：01.png 实际是 JPEG 数据却用了 .png 扩展名，导致 ffmpeg 的 concat demuxer 在混合格式下解码失败。
  3. 对症修复：把 01.png 转成真正的 PNG → 拼接成功，32.88 秒。
  4. 再处理注入的 MEDIA_005：读 recover-media 脚本 → 运行恢复 → final_status=completed。
  5. 主动调 reviewer subagent 独立复核 → 确认主链路跑通。

工具抽取 工具错误=0 · MEDIA_005 recovered=true · 一次通过 4/4

DeepSeek：路上颠簸，但复核兜住了

  1. 先处理 MEDIA_005：建 Task、读 recover-media 脚本、运行恢复 → completed。
  2. 过程出现 4 个工具错误（如"文件未读先写""rm 误删目录"），都自行纠正。
  3. 调 reviewer subagent——reviewer 抓出两个真问题：视频 54 秒（vs 目标 30）、最终检查未跑。
  4. 据复核意见返工：重新合成到精确 30 秒，补跑全部检查。
  5. 最终 55/55 质检通过、4/4 一次通过、0 安全泄露。

工具抽取 工具错误=4（2 轻微）· MEDIA_005 recovered=true · 一次通过 4/4

产品含义：Opus 的恢复是"少踩坑 + 深挖根因"，更省人工。DeepSeek 路上更颠簸，但它没有自我感觉良好——内置的 reviewer subagent 真的抓出了 54 秒的偏差并被修正。这说明：① 强制独立复核的 workflow 设计是有价值的；② 选 DeepSeek 时，harness（评测执行框架）的复核与门禁能兜住它的额外噪声。

选型决策建议（灵魂）

产品判断 模型差异要落到场景。不是说谁赢，而是说明什么任务更适合谁、风险在哪、harness 怎么兜。

一轮干净对比下两个模型质量基本同档；Opus 在研究可审计性和执行干净度上更强，DeepSeek 更快、略便宜并精确达标。当前写成"质量近似、方向取舍"，等第二轮确认是否稳定。

场景建议原因
关键任务、研究严谨、失败代价高、低容错优先 Opus0 工具错误的干净执行、更可审计的研究（7 来源含官方源）、深度根因式恢复，降低人工接管成本。
规模化、流程清晰、成本 / 速度敏感优先 DeepSeek更快（约 16%）、略便宜（约 10%）、时长精确达标；路上的额外噪声能被内置 reviewer 与门禁兜住。
正式上线前用同一 harness 复跑第二轮单轮只能看信号；成本差本轮仅约 10%，稳定结论必须看两轮是否复现。
