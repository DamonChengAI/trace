# 参考原则：Agent Eval 怎么设计

> ⚠️ **已过期，仅作背景参考**：本文含"六层工作流"旧口径，已被 `plans/round2-refined-eval-plan.md` 取代。开发以权威方案为准，不要把"六层"带入。

来源：[Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

这份文档只服务本次作业，不做文章复述。它回答一个问题：怎样把“两个模型驱动 Claude Code 做同一任务”设计成一个可解释的 agent eval。

## 1. 先定义评测对象

本次评测要固定这些对象：

- Task：同一个六层工作流任务。
- Trial：Opus 和 DeepSeek 各执行一次；时间允许时可重复。
- Trace / Transcript：Claude Code 全部执行过程。
- Outcome：最终项目状态和可展示产物。
- Grader：检查 outcome 和 trace 的评分逻辑。
- Harness：Claude Code、项目、prompt、工具权限和初始环境。

这样讲时更专业：评测对象是模型在同一 Claude Code harness 下的表现，避免凭感觉比较两段输出。

## 2. 先看 Outcome，再读 Trace

最终结果必须先能验收：

- 页面是否完成。
- 真实视频是否生成。
- storyboard 是否可展示。
- 六层报告是否完整。
- 测试和检查是否通过。

Trace 用来解释原因：为什么成功、为什么失败、失败在哪一步、模型有没有修复、是否依赖了错误路径。

## 3. Grader 要组合使用

本次不要只靠人工主观判断，也不要只靠测试。

建议三类 grader：

- 确定性检查：文件、脚本、测试、六层完整性、密钥泄露检查。
- Trace 行为检查：是否读规则、使用工具、调用 skill、触发检查、处理失败。
- 人工产品判断：六层图和报告是否能被产品岗面试官快速理解。

这样既有可复验结果，也保留产品判断空间。

## 4. 不按固定路径死扣

不要要求模型必须按某个固定顺序调用工具。模型可能用不同路径完成同一目标。

更稳的判断方式：

- outcome 是否达标；
- 关键能力是否有证据；
- 失败是否被发现和修复；
- 安全边界是否被守住；
- 结果是否能被产品岗解释清楚。

## 5. 环境要稳定

两个模型必须使用：

- 同一个起始 commit；
- 同一份任务 prompt；
- 同样的工具权限；
- 同样的 API key 注入方式；
- 同样的检查命令；
- 隔离的执行目录或回滚机制。

第二个模型不能看到第一个模型的结果，避免污染对比。

## 6. 任务要足够明确

如果任务描述含糊，模型失败可能是任务设计失败。

本次任务必须明确：

- 六层名称固定。
- 必须生成真实视频样例。
- 必须保留 storyboard。
- 必须输出 Markdown 和 JSON。
- 必须有正常样例和有问题样例。
- 必须运行检查。
- API key 不能进入仓库、报告或 trace 摘要。

## 7. 报告不要只给分

最终对比报告要解释差异背后的原因：

- 是模型没读规则；
- 是模型读了但没执行；
- 是工具使用失败；
- 是测试暴露问题；
- 是任务约束不够清楚；
- 是环境或 provider 造成干扰；
- 是结果完成但产品表达不够好。

这部分是面试里最有价值的内容。

## 8. 本次作业的评测口径

一句话：

```text
用可验收 outcome 证明任务完成，用 trace 解释模型差异，用产品判断说明这些差异对生产力 Agent 的真实影响。
```
