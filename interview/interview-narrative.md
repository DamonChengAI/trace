# 面试讲解方案

## 一句话

这是一个面向豆包 Agent 生产力评测产品岗的小型评测工具：我让 Opus 和 DeepSeek 在 Claude Code 里做同一个 30 秒视频生成任务，用 trace（执行轨迹）判断谁更适合复杂生产力 Agent（智能体）场景。

## 工具是什么

工具本体是一个 trace comparator（执行轨迹对比器）和 grader（评测器）。

它读取两个模型的 raw trace（原始执行轨迹）、manifest（产物清单）、检查结果和最终视频，把原始过程整理成三类输出：

```text
metrics.json：结构化指标
report.md：产品复盘报告
interview-review.html：面试讲解页
```

视频只是任务结果的证明。工具真正判断的是：模型有没有读懂规则、有没有正确用 Claude Code 能力、失败后能不能恢复、最终表达能不能让业务方理解。

## Workflow 怎么工作

workflow（工作流）可以理解成一条任务流水线：

```text
读规则 -> 查公开信息 -> 写分镜 -> 生成 3 张图片和音轨 -> 拼成 30 秒视频 -> 跑检查 -> 写报告
```

这个任务对面试官很好理解：一句需求变成一条视频。它又足够完整，可以测出模型是否会读项目约束、复用脚本、处理失败、跑 hook（钩子检查）和 subagent（子代理）复核。

## 为什么用 Trace 评

产品上要回答的是：哪个模型更稳定地把一句需求推进成可交付结果，过程中风险在哪里，人工接管成本有多高，哪些能力可以沉淀成评测标准。

单纯调用一次视频接口太薄，测不出这些差异，也测不出 Claude Code 的核心能力。

这个任务要求模型在已有 `workflow-sandbox` 里完整走一遍视频生成流程：

```text
理解需求 -> 写分镜 -> 生成多张图片 -> 生成对应音频 -> 拼接成片 -> 处理失败 -> 跑 hook -> 做 subagent 审查 -> 安全检查 -> 交付报告
```

这条流程足够暴露模型差异，但对面试官来说很好理解：就是从一句需求到一条可交付视频。

音频口径要讲清楚：当前两个最终 MP4 都有音轨，但真实 TTS（文字转语音）口播还没接入。本轮先把音频资产和视频合成链路作为 workflow 证据，等展示结构确认后再加音频 API。

## 现场展示顺序

1. 先给一句话结论：两边都交付了视频，Opus 过程更聚焦，DeepSeek 恢复能力可用但人工复核成本更高。
2. 讲我解决问题的思路：先定义产品问题，再设计受控 workflow，再采集 trace，最后做工具把 trace 变成证据。
3. 讲工具解决什么问题：最终视频只能说明结果，工具要补上过程证据、评分和结论信源。
4. 展示评测证据地图：把 workflow 环节、能力覆盖、trace 证据、工具作用、两边结果和结论放在一张表里。
5. 展示评分方法：每个维度先讲为什么这么定，再讲两个模型为什么得这个分。
6. 展示结论证据卡：每个结论都能反查指标和信源。
7. 最后讲怎么验证：先看 metrics，再看证据地图和评分，必要时反查 raw trace。

## 重点讲法

```text
我把视频生成当作受控生产流程，不把它当审美题。

我看的是 trace（执行轨迹）：它有没有读项目规则，有没有复用已有 workflow（工作流），有没有用脚本和检查命令，有没有处理失败，有没有触发 hook（钩子检查）和 subagent（子代理）审查，有没有守住密钥和路径边界，最后能不能把结果讲成业务方能理解的交付报告。

我的工具把这些过程证据转成 6 个维度：结果完成、上下文理解、Claude Code 能力、执行质量、风险控制、产品表达。这样面试官不用读原始日志，也能看到两个模型的真实差异。

最重要的是，我不只给结论，还把结论和信源绑在一起。比如“Opus 研究证据更可审计”，对应的是 research URL 数：Opus 6 个，DeepSeek 0 个；“DeepSeek 恢复成本更高”，对应的是去重工具错误和严重错误数量。
```

## 避免的讲法

- 不讲“六层可视化页面”。
- 不讲复杂 dashboard。
- 不把 Claude Code 能力讲成工具清单。
- 不用视频审美判断模型优劣。
- 不说这是一个完整视频生产系统。
